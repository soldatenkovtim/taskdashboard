# Контур

Русскоязычный менеджер задач небольшой команды. Next.js App Router, React, TypeScript, Tailwind CSS, Supabase Auth и PostgreSQL. Подготовлен для Vercel. Визуальный стиль: кремовый, оливковый, приглушённый розовый и красный, редакционная типографика и тонкие линии по предоставленному референсу.

## Текущий статус

Исходный код, SQL-миграция, серверные операции и автоматические тесты готовы. Главная `/` — публичный лендинг; `/workspace` — защищённая рабочая панель. Без переменных Supabase вход и регистрация недоступны, форма объясняет причину. Это **не демонстрация с фиктивной авторизацией**: вход, создание и сохранение задач требуют настоящего Supabase. localStorage и файлы для рабочих данных не используются. Облачная база и Vercel пока не настроены. Сквозные сценарии с письмами и двумя реальными аккаунтами необходимо проверить после подключения.

## Локальный запуск

Требуется Node.js 22.13+ (проверено на 24).

```sh
npm ci
cp .env.example .env.local
npm run dev
```

Откройте адрес, который напечатает Next.js. Для production:

```sh
npm test
npm run build
npm start
```

Сборка использует Webpack: в текущей локальной среде Turbopack при production-сборке завершался ошибкой создания служебного сокета. Это поддерживаемый режим Next.js; Vercel использует тот же `npm run build`.

## Supabase

1. Создайте отдельный проект в Supabase Dashboard. Сохраните пароль базы в своём менеджере паролей; приложению он не нужен.
2. В SQL Editor выполните **целиком и один раз** `supabase/migrations/001_initial.sql`. Миграция транзакционная. Если пользуетесь Supabase CLI, примените миграцию штатным `supabase db push` после привязки проекта.
3. В настройках API скопируйте Project URL и publishable key (для старого проекта подойдёт anon key). Заполните `.env.local`:

```dotenv
NEXT_PUBLIC_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=YOUR_PUBLIC_KEY
NEXT_PUBLIC_SITE_URL=http://localhost:3000
```

Используйте один и тот же origin в браузере и `NEXT_PUBLIC_SITE_URL`. Например, при `http://127.0.0.1:3000` укажите именно его. Не добавляйте завершающий `/`.

4. В Supabase Auth включите Email/password, подтверждение email и задайте минимальную длину пароля 8 символов.
5. В Auth → URL Configuration задайте Site URL приложения и добавьте Redirect URLs:
   - `http://localhost:3000/auth/callback`
   - `http://localhost:3000/auth/callback?next=/auth?mode=update`
   - Аналогичные адреса с production-доменом после деплоя.
6. Проверьте настройки доставки писем Supabase. Для реальных сотрудников настройте свой SMTP, если встроенная доставка вашего проекта ограничена. Приложение отправляет только письма подтверждения и восстановления через Supabase Auth; рабочих email-рассылок нет.
7. Перезапустите `npm run dev` после изменения переменных.

`service_role` и secret key не требуются работающему веб-приложению; привилегированный ключ используется только отдельной командой первичного создания администратора. Не помещайте их в переменные `NEXT_PUBLIC_*`.

## Локальная проверка без базы

В `.env.local` включите `DEV_PREVIEW_ENABLED=true` и запустите `npm run dev`. На `/auth` появятся две кнопки: предпросмотр администратора и сотрудника. Прямые ссылки: `/preview?role=admin` и `/preview?role=employee`. Это только интерфейс, без авторизации и сохранения задач. API продолжает требовать настоящий Supabase. В production маршрут всегда возвращает 404, даже если флаг включён.

## Первый администратор: локально и на проде

Первый администратор создаётся отдельной командой владельца, а не публичной регистрацией. Роль хранится в `public.profiles`; переменные не дают прав произвольным посетителям.

1. Создайте Supabase и примените миграции `001_initial.sql`, `002_playful_reactions.sql`, `003_profile_avatars.sql`.
2. Скопируйте `admin.env.example` в `.env.admin.local` (игнорируется Git).
3. Заполните URL нужного проекта, `SUPABASE_SECRET_KEY` (secret key или legacy service_role), `ADMIN_EMAIL`, `ADMIN_PASSWORD` (минимум 12 символов), `ADMIN_NAME`.
4. Выполните `npm run admin:create`. Команда создаёт аккаунт с подтверждённой почтой и назначает `admin/active`. Она не отправляет письмо и не запускается автоматически при старте сайта или сборке.
5. Войдите через `/auth` с заданными email и паролем. Права уже назначены. Для существующего аккаунта укажите его UUID в `ADMIN_USER_ID` и подтверждённый `ADMIN_EMAIL`: пароль не меняется. При несовпадении почты команда отказывается работать.
6. Удалите пароль и привилегированный ключ из `.env.admin.local` после настройки. Для обычной работы сайта они не нужны. Никогда не добавляйте к ним `NEXT_PUBLIC_` и не размещайте их в клиентском коде.

**Локально:** публичные настройки Supabase находятся в `.env.local`, `NEXT_PUBLIC_SITE_URL=http://localhost:3000`.
**Прод:** те же три публичные переменные в настройках хостинга, `NEXT_PUBLIC_SITE_URL=https://ваш-домен`. Создание администратора выполняется оператором с URL и ключом production-проекта, а не через общедоступную страницу. В Supabase разрешите callback URL локального адреса и production-домена (см. выше).

Если оба окружения используют один Supabase, аккаунты и задачи общие. Для независимых тестовых данных используйте отдельный проект и создайте в нём отдельного администратора той же командой.

Обычная регистрация по-прежнему создаёт только `employee/pending`; администратор открывает доступ сотрудникам в разделе «Команда». Никто не получает админские права за то, что зарегистрировался первым. Приложение рассчитано на одну команду на проект Supabase.

- Доска из четырёх статусов, drag-and-drop, смена статуса из карточки и drawer, мобильные вкладки колонок.

- Поиск, фильтр сотрудника, просрочек и статуса (через показатели), сортировка по сроку.
- Первоначальный и текущий согласованный срок, запросы переноса, причины, согласование, отклонение и альтернативная дата.

- Обзор команды, доля завершения в срок, переносы и накопленное время в статусах, отклонение от исходного и последнего сроков.
- Пустые состояния, загрузка, сообщения ошибок, блокировка повторного сохранения и проверка версии задачи.

## Гарантии данных

Все изменения проходят через `task_action`: PostgreSQL проверяет текущего пользователя, активность, роль и исполнителя. Изменения, уведомления и события выполняются в одной транзакции. Блокировка строки и `version` защищают от потерянных обновлений. Клиенты не имеют прямых прав INSERT/UPDATE/DELETE на рабочие таблицы, даже с валидным JWT. SECURITY DEFINER-функции имеют фиксированный `search_path`; внутренние функции недоступны клиентам.

RLS ограничивает задачи и связанные записи исполнителем или активным администратором. Ожидающие/заблокированные аккаунты видят только собственный профиль. Администратор принимает только задачу на проверке. До принятия необходимо разрешить ожидающий запрос срока. Завершённый срок не редактируется, поэтому итоговая аналитика не меняется задним числом.

Даты хранятся как timestamptz в UTC и показываются по Москве. Официальная просрочка рассчитывается сервером базы. UI синхронизирует часы с `serverNow`. `workspace_data` получает единый согласованный снимок с применением RLS, без лимита 1000 строк PostgREST, который мог бы обрезать историю.

Факт просрочки фиксируется при следующем чтении рабочего пространства или изменении задачи. В событии сохраняются момент обнаружения и фактическая граница срока (`occurred_at`). Перед переносом, принятием и архивированием система обязательно фиксирует старую просрочку. Отдельного фонового планировщика нет; при отсутствии открытых сессий запись события появляется при следующем обращении.

При конфликте редактирования изменения не сохраняются, введённый текст остаётся в форме. Скопируйте правки, закройте карточку и откройте её заново для загрузки актуальной версии.

## Проверки

`npm test` запускает реальные SQL-операции и RLS в изолированном PostgreSQL (PGlite). Схема `auth` и `auth.uid()` эмулируют пользовательскую идентичность только внутри тестов; рабочее приложение использует настоящий Supabase Auth. Данные тестов не попадают в приложение.

Проверяются права, регистрация без повышения роли, принятие задач, запросы сроков, сохранение просрочек, уведомления, блокировка, целостность транзакций и конфликты версий, а также накопление повторных интервалов работы/проверки. Тесты не заменяют проверку доставки email и развёрнутого сервиса.

## Vercel

1. Сохраните проект в Git-репозиторий и импортируйте его в Vercel как Next.js.
2. Выберите Node.js 24, Install Command `npm ci`, Build Command `npm run build`.
3. Задайте три переменные из `.env.example` для Production. `NEXT_PUBLIC_SITE_URL` должен содержать окончательный HTTPS-домен Vercel или ваш собственный домен.
4. Добавьте production callback URLs в Supabase Auth, как указано выше.
5. Выполните Deploy. Изменения `NEXT_PUBLIC_*` требуют новой сборки.
6. Проверьте сценарии ниже в двух независимых браузерных профилях.

## Приёмка после подключения

- Сотрудник регистрируется, подтверждает email, ожидает доступа; администратор предоставляет доступ.
- Администратор назначает задачу, сотрудник видит её после обновления и получает уведомление.
- Сотрудник создаёт собственную задачу и предлагает срок; до решения официальный срок отсутствует.
- Отклонение переноса сохраняет текущий срок; одобрение меняет текущий, сохраняя исходный и прежнюю просрочку.
- Сотрудник не видит чужую задачу по UUID, не архивирует, не принимает и не редактирует историю.
- Review не скрывает просрочку; возврат требует причины; принятие фиксирует время и опоздание.
- Две вкладки с одной версией не могут незаметно перезаписать друг друга.
- Перезагрузка сохраняет задачи, события, комментарии, решения и уведомления.
- Восстановление пароля проходит по письму; закрытый доступ прекращает чтение данных.
- На телефоне колонки переключаются вкладками; действия доступны без drag-and-drop.

- `app/` — страницы, обработчики API и действия авторизации.
- `components/` — доска, формы, drawer и история.

## Playful Rewards & Reactions

Дополнительная функция включается отдельно для каждого аккаунта: нажмите профиль внизу боковой панели → **Playful reactions: ON / OFF**. По умолчанию OFF, включая администратора. Выход из аккаунта теперь расположен в панели профиля. Без Supabase переключатель недоступен: локально настройка не подменяется.

Для уже созданной базы выполните только новую миграцию `supabase/migrations/002_playful_reactions.sql`. Для новой базы примените сначала `001_initial.sql`, затем `002_playful_reactions.sql`. Первая миграция повторно не запускается. Новое поле автоматически попадает в существующий снимок `workspace_data`. Права и операции задач не меняются; отдельная функция настроек может менять только предпочтение текущего пользователя.

- `components/reaction-popup.tsx` — переиспользуемый поп-ап с ручным закрытием, автоматическим закрытием через 4,5 секунды, без звука и перехвата фокуса. Поддерживает открытый drawer, уменьшение движения и закрытие при уходе с вкладки.
- `lib/reactions.ts` — конфигурация десяти реакций для двух ролей, выбор одной реакции на операцию и подавление повторов.
- `public/reactions/` — папка настоящих GIF, animated WebP, MP4 и WebM. Подключены десять оригинальных покадровых GIF в стиле нуарного кабаре. Предпросмотр: `/reactions`; исходники и запросы: `assets/reactions/v2/`; пересборка: `node scripts/build-reactions-v2.mjs`. Подробности — в `public/reactions/README.md`.

Администратор получает реакцию только после успешного ответа операции. Создание с назначением другому участнику даёт `YOU'RE THE BOSS.`, создание для себя — `MAKE THEM WORK.`. Принятие, возврат и согласование имеют отдельные реакции. Ошибка, отмена и простое редактирование без смены исполнителя не дают реакций.

Сотрудник получает реакции из существующих серверных уведомлений, включая действия администратора в другом браузере. Задержка — до интервала текущего опроса (30 секунд). Для принятой задачи с официальным сроком используется серверный `completed_late`, для задачи без срока — `GOOD JOB, BABY.`. Отклонение срока не имеет реакции, поскольку текст для него не задан.

Первая успешная загрузка устанавливает исходную точку: старые, в том числе непрочитанные, уведомления не воспроизводятся. Обновление страницы снова устанавливает исходную точку. События, пришедшие при OFF или в скрытой вкладке, не накапливаются для последующего показа. При включении не воспроизводится накопленное. Один пакет опроса сворачивается в одну последнюю подходящую реакцию; очереди поп-апов нет. Реакции — краткие эффекты, постоянная история остаётся в задачах и уведомлениях.

Тесты проверяют новую миграцию и сохранение личной настройки, подавление исторических/повторных событий, приоритеты реакций, серверную классификацию опоздания и допустимые типы медиа. Сквозная проверка двух настоящих аккаунтов и доставки событий остаётся этапом подключения Supabase. Тест медиа проверяет наличие разных кадров, зацикливание и размер каждого GIF до 2 MB.

Награда `over-ten.gif` показывается при достижении 10 задач за последние 72 часа по серверному времени: администратору — по дате создания его задач, сотруднику — по дате принятия выполненных работ. Архив учитывается. Пока счёт остаётся не ниже 10, повторов нет; после снижения ниже порога новое достижение снова доступно. Первая загрузка устанавливает исходный счёт; старые достижения и достижения при OFF не воспроизводятся. GIF длится 5,2 секунды, поп-ап — 5,6 секунды.

## Аватарки профиля

Профиль → «Ваша аватарка»: пять локальных GIF из `public/avatars/` или инициалы. Изменение автоматически сохраняется через `/api/preferences` и `set_avatar`; функция принимает только ID из каталога и меняет только профиль текущего пользователя. Примените миграцию `003_profile_avatars.sql` после 001 и 002. Аватар виден в боковой панели, задачах и команде. При `prefers-reduced-motion` используется статичный WebP. В локальном предпросмотре выбор действует только до перезагрузки, без записи в базу.

## Обновление: обязательные реакции и аватары предпросмотра

Примените `004_reactions_always_on.sql` после 003: реакции всегда ON для существующих и новых профилей, функция отключения удалена. Старое значение OFF клиентом игнорируется. Галерея `/reactions` проверяет серверную сессию и доступна только активному администратору. Для локального админского предпросмотра используется `/reactions?preview=admin`, исключение работает только при включённом dev-предпросмотре и никогда в production.

Аватары предпросмотра сохраняются в localStorage отдельно для ролей, без обращения к базе. Настоящие аккаунты по-прежнему сохраняют аватар на сервере.

## Награда за серию посещений

Миграция `005_visit_streak.sql`: активный пользователь любой роли получает GIF на 8-й календарный день подряд по Москве. Счёт обновляется при открытии рабочей панели после входа, не фоновым опросом и не гостевым посещением лендинга. Повторный вход в тот же день ничего не добавляет. На 9-й и следующих днях награда не повторяется; пропуск дня начинает новую серию. Дата определяется базой, запись профиля блокируется на время изменения для защиты от нескольких вкладок. Только в локальном предпросмотре администратора кнопка «Показать награду за 8 дней» демонстрирует поп-ап без изменения счёта. Примените миграции 001–005 по порядку при подключении Supabase.


### Обязательный срок новых задач

Примените `supabase/migrations/006_required_task_deadline.sql` после предыдущих миграций. Создание задачи требует дату и время: проверка действует в форме, API и функции базы `task_action`. Для сотрудника срок по-прежнему является предложением до согласования администратором. Существующие задачи без срока миграция не изменяет.


### Серия посещений: 16 дней и возвращение

Миграция `007_visit_streak_sixteen.sql` расширяет учёт посещений: `sixteen-days.gif` показывается один раз на 16-й день подряд, `streak-broken.gif` — один раз при возвращении после пропуска календарного дня, если прежняя серия была 16 дней или больше. На этом входе начинается новая серия с первого дня. Часовой пояс — Москва; награда за 8 дней сохраняется. Обе реакции доступны администратору и сотруднику и представлены в галерее реакций. GIF импортированы без изменений; длительность каждой — 5,2 секунды.

## Файлы проектов

Примените `supabase/migrations/009_project_files.sql` после миграций 001–008 в SQL Editor своего Supabase-проекта. Она создаёт проекты, материалы, обсуждения и **приватный** bucket `project-files` (25 МБ на файл), а также RLS-политики. Service role приложению не нужен. До применения миграции раздел показывает ошибку настройки; без Supabase доступен только несохраняемый предпросмотр.

- В меню «Файлы проектов» создайте проект и добавьте документ или HTTP(S)-ссылку с описанием. Можно связать материал с доступной задачей, включая старую/архивную, либо оставить без задачи.
- В карточке задачи есть «Материалы задачи». Вложения до принятия видят текущий исполнитель и активные администраторы. Готовые вложения публикуются триггером в одной транзакции с принятием задачи; возврат на доработку их не публикует.
- Файл загружается напрямую в приватный Supabase Storage, без передачи через лимит тела serverless-функции. Сначала резервируется запись, затем загружается объект и подтверждается завершение. Если задачу приняли в процессе загрузки, подтверждение опубликует файл после загрузки.
- У принятой задачи новые материалы сразу публикуются. Материалы без задачи публикуются напрямую — это путь для исторических файлов. Все опубликованные материалы доступны активной команде. Это общее пространство команды, не система отдельных закрытых проектов.
- Поиск работает по названию, описанию и имени файла, с фильтром проекта и пагинацией по 50 материалов. Обсуждения доступны рядом с материалом. Короткие подписанные ссылки на скачивание действуют 60 секунд; документы отдаются как загрузка.
- Незавершённые загрузки не публикуются: автор видит их в задаче или в общем списке без фильтров (для материалов без задачи). Если объект загрузился, но подтверждение прервалось, нажмите «Подтвердить загрузку». Если сам объект не загрузился, добавьте файл заново. Удаление и перезапись объектов намеренно не включены, чтобы не потерять принятые материалы; незавершённые записи сохраняются для диагностики.
- Проекты не связаны с существующей моделью задач: у материала свой проект, а задача — необязательная ссылка. История задач, роли и процедуры согласования не изменены.

`tests/materials.test.ts` проверяет RLS, приватные объекты, публикацию при принятии, возврат, историческую загрузку, загрузку после принятия, запрет подмены и блокировку пользователя в локальном PostgreSQL (PGlite). Реальные загрузки в Supabase Storage и браузерный сценарий необходимо проверить после подключения проекта; тестовый storage schema моделирует политики, а не внешний Storage-сервис.

## Проверка плотности рабочего пространства

Только при `NODE_ENV=development` и `DEV_PREVIEW_ENABLED=true` доступны `/preview?role=admin&count=5`, `count=15`, `count=30` (аналогично `role=employee`). Наборы содержат явно обозначенные демонстрационные задачи, не загружаются из production и не сохраняются. В production `/preview` возвращает 404 даже с этими параметрами; API по-прежнему проверяют сессию и серверные роли. В реальном `/workspace` параметры предпросмотра не используются.

KPI находятся только в «Обзоре команды». Показатели открывают фильтрованные задачи; выборки завершённых и перенесённых включают архивные задачи, чтобы соответствовать аналитическим итогам. Архивные карточки в таких выборках недоступны для перетаскивания и смены статуса. Для восстановления используется отдельное действие администратора в таблице архива. «Предложить другую дату» открывает существующую карточку с формой согласования — серверная процедура сроков не изменена.
