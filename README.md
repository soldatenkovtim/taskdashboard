# Контур

Русскоязычный менеджер задач небольшой команды. Next.js App Router, React, TypeScript, Tailwind CSS, Supabase Auth и PostgreSQL. Подготовлен для Vercel. Визуальный стиль: кремовый, оливковый, приглушённый розовый и красный, редакционная типографика и тонкие линии по предоставленному референсу.

## Текущий статус

Исходный код, SQL-миграция, серверные операции и автоматические тесты готовы. Без переменных Supabase открывается пустая доска с инструкцией подключения. Это **не демонстрация с фиктивной авторизацией**: вход, создание и сохранение задач требуют настоящего Supabase. localStorage и файлы для рабочих данных не используются. Облачная база и Vercel пока не настроены. Сквозные сценарии с письмами и двумя реальными аккаунтами необходимо проверить после подключения.

## Локальный запуск

Требуется Node.js 22.13+ (проверено на 24).

```sh
npm ci
cp .env.example .env.local
npm run dev
```

Откройте адрес, который напечатает Next.js. Для production:

```sh
npm test
npm run build
npm start
```

Сборка использует Webpack: в текущей локальной среде Turbopack при production-сборке завершался ошибкой создания служебного сокета. Это поддерживаемый режим Next.js; Vercel использует тот же `npm run build`.

## Supabase

1. Создайте отдельный проект в Supabase Dashboard. Сохраните пароль базы в своём менеджере паролей; приложению он не нужен.
2. В SQL Editor выполните **целиком и один раз** `supabase/migrations/001_initial.sql`. Миграция транзакционная. Если пользуетесь Supabase CLI, примените миграцию штатным `supabase db push` после привязки проекта.
3. В настройках API скопируйте Project URL и publishable key (для старого проекта подойдёт anon key). Заполните `.env.local`:

```dotenv
NEXT_PUBLIC_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=YOUR_PUBLIC_KEY
NEXT_PUBLIC_SITE_URL=http://localhost:3000
```

Используйте один и тот же origin в браузере и `NEXT_PUBLIC_SITE_URL`. Например, при `http://127.0.0.1:3000` укажите именно его. Не добавляйте завершающий `/`.

4. В Supabase Auth включите Email/password, подтверждение email и задайте минимальную длину пароля 8 символов.
5. В Auth → URL Configuration задайте Site URL приложения и добавьте Redirect URLs:
   - `http://localhost:3000/auth/callback`
   - `http://localhost:3000/auth/callback?next=/auth?mode=update`
   - Аналогичные адреса с production-доменом после деплоя.
6. Проверьте настройки доставки писем Supabase. Для реальных сотрудников настройте свой SMTP, если встроенная доставка вашего проекта ограничена. Приложение отправляет только письма подтверждения и восстановления через Supabase Auth; рабочих email-рассылок нет.
7. Перезапустите `npm run dev` после изменения переменных.

`service_role` и secret key приложению не требуются. Не помещайте их в переменные `NEXT_PUBLIC_*`.

## Первый администратор

Публичного выбора роли нет. Зарегистрируйтесь через `/auth`, подтвердите email. Аккаунт получит роль `employee` и состояние `pending`.

В защищённом SQL Editor Supabase, доступном владельцу проекта, выполните, подставив **свой проверенный email**:

```sql
update public.profiles
set role = 'admin', access_status = 'active'
where id = (
  select id from auth.users
  where email = 'owner@your-company.ru'
    and email_confirmed_at is not null
)
returning id, name, role, access_status;
```

Убедитесь, что возвращена ровно одна строка. Перезагрузите приложение. Новых сотрудников подтверждайте в разделе «Команда». Назначение дополнительных администраторов возможно только владельцем базы через защищённый SQL Editor.

Приложение рассчитано на **одну команду на проект Supabase**. Для независимых организаций используйте разные проекты; мультитенантность в эту версию не входит.

## Что реализовано

- Регистрация, email-подтверждение, вход, выход, восстановление пароля, ожидание доступа и блокировка.
- Доска из четырёх статусов, drag-and-drop, смена статуса из карточки и drawer, мобильные вкладки колонок.
- Создание, административное редактирование, назначение, приоритет, описание Markdown.
- Поиск, фильтр сотрудника, просрочек и статуса (через показатели), сортировка по сроку.
- Первоначальный и текущий согласованный срок, запросы переноса, причины, согласование, отклонение и альтернативная дата.
- Приём работы администратором, возврат с обязательной причиной, архив и восстановление.
- Хронологическая неизменяемая история, комментарии, сохранённые уведомления с опросом каждые 30 секунд.
- Обзор команды, доля завершения в срок, переносы и накопленное время в статусах, отклонение от исходного и последнего сроков.
- Пустые состояния, загрузка, сообщения ошибок, блокировка повторного сохранения и проверка версии задачи.

## Гарантии данных

Все изменения проходят через `task_action`: PostgreSQL проверяет текущего пользователя, активность, роль и исполнителя. Изменения, уведомления и события выполняются в одной транзакции. Блокировка строки и `version` защищают от потерянных обновлений. Клиенты не имеют прямых прав INSERT/UPDATE/DELETE на рабочие таблицы, даже с валидным JWT. SECURITY DEFINER-функции имеют фиксированный `search_path`; внутренние функции недоступны клиентам.

RLS ограничивает задачи и связанные записи исполнителем или активным администратором. Ожидающие/заблокированные аккаунты видят только собственный профиль. Администратор принимает только задачу на проверке. До принятия необходимо разрешить ожидающий запрос срока. Завершённый срок не редактируется, поэтому итоговая аналитика не меняется задним числом.

Даты хранятся как timestamptz в UTC и показываются по Москве. Официальная просрочка рассчитывается сервером базы. UI синхронизирует часы с `serverNow`. `workspace_data` получает единый согласованный снимок с применением RLS, без лимита 1000 строк PostgREST, который мог бы обрезать историю.

Факт просрочки фиксируется при следующем чтении рабочего пространства или изменении задачи. В событии сохраняются момент обнаружения и фактическая граница срока (`occurred_at`). Перед переносом, принятием и архивированием система обязательно фиксирует старую просрочку. Отдельного фонового планировщика нет; при отсутствии открытых сессий запись события появляется при следующем обращении.

При конфликте редактирования изменения не сохраняются, введённый текст остаётся в форме. Скопируйте правки, закройте карточку и откройте её заново для загрузки актуальной версии.

## Проверки

`npm test` запускает реальные SQL-операции и RLS в изолированном PostgreSQL (PGlite). Схема `auth` и `auth.uid()` эмулируют пользовательскую идентичность только внутри тестов; рабочее приложение использует настоящий Supabase Auth. Данные тестов не попадают в приложение.

Проверяются права, регистрация без повышения роли, принятие задач, запросы сроков, сохранение просрочек, уведомления, блокировка, целостность транзакций и конфликты версий, а также накопление повторных интервалов работы/проверки. Тесты не заменяют проверку доставки email и развёрнутого сервиса.

## Vercel

1. Сохраните проект в Git-репозиторий и импортируйте его в Vercel как Next.js.
2. Выберите Node.js 24, Install Command `npm ci`, Build Command `npm run build`.
3. Задайте три переменные из `.env.example` для Production. `NEXT_PUBLIC_SITE_URL` должен содержать окончательный HTTPS-домен Vercel или ваш собственный домен.
4. Добавьте production callback URLs в Supabase Auth, как указано выше.
5. Выполните Deploy. Изменения `NEXT_PUBLIC_*` требуют новой сборки.
6. Проверьте сценарии ниже в двух независимых браузерных профилях.

## Приёмка после подключения

- Сотрудник регистрируется, подтверждает email, ожидает доступа; администратор предоставляет доступ.
- Администратор назначает задачу, сотрудник видит её после обновления и получает уведомление.
- Сотрудник создаёт собственную задачу и предлагает срок; до решения официальный срок отсутствует.
- Отклонение переноса сохраняет текущий срок; одобрение меняет текущий, сохраняя исходный и прежнюю просрочку.
- Сотрудник не видит чужую задачу по UUID, не архивирует, не принимает и не редактирует историю.
- Review не скрывает просрочку; возврат требует причины; принятие фиксирует время и опоздание.
- Две вкладки с одной версией не могут незаметно перезаписать друг друга.
- Перезагрузка сохраняет задачи, события, комментарии, решения и уведомления.
- Восстановление пароля проходит по письму; закрытый доступ прекращает чтение данных.
- На телефоне колонки переключаются вкладками; действия доступны без drag-and-drop.

## Структура

- `app/` — страницы, обработчики API и действия авторизации.
- `components/` — доска, формы, drawer и история.
- `lib/` — Supabase SSR, типы и расчёт времени.
- `supabase/migrations/` — версия схемы, RLS и атомарные функции.
- `tests/` — SQL-интеграционные тесты и расчёты.

## Playful Rewards & Reactions

Дополнительная функция включается отдельно для каждого аккаунта: нажмите профиль внизу боковой панели → **Playful reactions: ON / OFF**. По умолчанию OFF, включая администратора. Выход из аккаунта теперь расположен в панели профиля. Без Supabase переключатель недоступен: локально настройка не подменяется.

Для уже созданной базы выполните только новую миграцию `supabase/migrations/002_playful_reactions.sql`. Для новой базы примените сначала `001_initial.sql`, затем `002_playful_reactions.sql`. Первая миграция повторно не запускается. Новое поле автоматически попадает в существующий снимок `workspace_data`. Права и операции задач не меняются; отдельная функция настроек может менять только предпочтение текущего пользователя.

- `components/reaction-popup.tsx` — переиспользуемый поп-ап с ручным закрытием, автоматическим закрытием через 3 секунды, без звука и перехвата фокуса. Поддерживает открытый drawer, уменьшение движения и закрытие при уходе с вкладки.
- `lib/reactions.ts` — конфигурация десяти реакций для двух ролей, выбор одной реакции на операцию и подавление повторов.
- `public/reactions/` — папка настоящих GIF, animated WebP, MP4 и WebM. Сейчас файлов нет: все реакции **текстовые**. Инструкция добавления находится в `public/reactions/README.md`.

Администратор получает реакцию только после успешного ответа операции. Создание с назначением другому участнику даёт `YOU'RE THE BOSS.`, создание для себя — `MAKE THEM WORK.`. Принятие, возврат и согласование имеют отдельные реакции. Ошибка, отмена и простое редактирование без смены исполнителя не дают реакций.

Сотрудник получает реакции из существующих серверных уведомлений, включая действия администратора в другом браузере. Задержка — до интервала текущего опроса (30 секунд). Для принятой задачи с официальным сроком используется серверный `completed_late`, для задачи без срока — `GOOD JOB, BABY.`. Отклонение срока не имеет реакции, поскольку текст для него не задан.

Первая успешная загрузка устанавливает исходную точку: старые, в том числе непрочитанные, уведомления не воспроизводятся. Обновление страницы снова устанавливает исходную точку. События, пришедшие при OFF или в скрытой вкладке, не накапливаются для последующего показа. При включении не воспроизводится накопленное. Один пакет опроса сворачивается в одну последнюю подходящую реакцию; очереди поп-апов нет. Реакции — краткие эффекты, постоянная история остаётся в задачах и уведомлениях.

Тесты проверяют новую миграцию и сохранение личной настройки, подавление исторических/повторных событий, приоритеты реакций, серверную классификацию опоздания и допустимые типы медиа. Сквозная проверка двух настоящих аккаунтов и доставки событий остаётся этапом подключения Supabase. Проверку визуального содержимого и плавности анимаций следует выполнить после добавления реальных медиа.
